# T1.3.1 Template formats, IDs and test vectors

**Task:** T1.3.1 (P1, WP1.3) · **Type:** Research · **Date:** 2026-09-22

**Question:** what exactly is in a skill template code and an equipment template code, what
are the ids M1 needs, and what does a real code decode to field by field?

**Method:** the skill format came from `research/Skills/Template.md`. Three wiki pages were
fetched, three seconds apart, with `robots.txt` checked first: Equipment template format,
Skill template format/Skill list, and `robots.txt` itself. Every decode below was produced
by running the format against the seven §20.1 codes; nothing is transcribed by hand.

`robots.txt` disallows `/index.php`, `/api.php`, `/load.php` and `Special:` pages, and allows
`/wiki/<Title>`. That is exactly what EXT-1 and EXT-2 already require, so no change is needed.

## 1. Skill template format (type 14)

| Field | Bits | Notes |
| --- | --- | --- |
| Template type | 4 | **14** (`0xE`) for a skill template |
| Version | 4 | 0 |
| Profession width code | 2 | `bits = code × 2 + 4` |
| Primary profession | n | 0 means none |
| Secondary profession | n | |
| Attribute count | 4 | |
| Attribute width code | 4 | `bits = code + 4` |
| *per attribute:* id | n | |
| *per attribute:* rank | 4 | the rank from **points only**, 0–12; runes are not in the code |
| Skill width code | 4 | `bits = code + 8` |
| *8 ×* skill id | n | 0 means an empty slot |
| Tail | 1 | always 0 |
| Padding | 0–5 | zero bits, to fill the last Base64 character |

Codes made before 2007-04-05 have only a 4-bit **version** header, with no type nibble.

**Bit order.** Each Base64 character gives six bits, **lowest bit first**, and each field's
value is assembled lowest bit first as well. Getting either backwards decodes to plausible
nonsense rather than an obvious failure, which is why the worked decode below matters.

The alphabet is standard Base64: `A–Z a–z 0–9 + /`. No padding characters are used.

## 2. Worked decode: the player's bar

`OQBTAUBPQaJ4EY6x0BAAAAAAuE`, field by field:

| Field | Bits | Value | Meaning |
| --- | --- | --- | --- |
| type | 4 | 14 | skill template |
| version | 4 | 0 | |
| profession width code | 2 | 0 | → 4 bits each |
| primary | 4 | 5 | **Mesmer** |
| secondary | 4 | 0 | **none** |
| attribute count | 4 | 3 | |
| attribute width code | 4 | 1 | → 5 bits each |
| attribute 0 | 5 + 4 | id 0, rank 10 | **Fast Casting 10** |
| attribute 1 | 5 + 4 | id 2, rank 12 | **Domination Magic 12** |
| attribute 2 | 5 + 4 | id 3, rank 8 | **Inspiration Magic 8** |
| skill width code | 4 | 4 | → 12 bits each |
| skills | 8 × 12 | 75, 39, 979, 934, 0, 0, 0, 2416 | Arcane Echo, Energy Surge, Mistrust, Unnatural Signet, (empty ×3), Air of Superiority |
| tail | 1 | 0 | |
| padding | 2 | 0 | 156 bits = 26 characters |

This is exactly what §17.2 predicts: Mesmer, no secondary, Fast Casting 10, Domination 12,
Inspiration 8. **The ranks are from points only** — the build's effective Domination 16 comes
from adding a superior rune and headgear afterwards (A-033), and none of that is in the code.

## 3. How the widths are chosen

This is the part T1.3.3 has to get right, because a code must **re-encode to the identical
string**. Decoding all seven §20.1 codes gives:

| Code | Prof code | Attr code | Max attr id | Skill code | Max skill id |
| --- | --- | --- | --- | --- | --- |
| Player | 0 → 4 bits | **1 → 5 bits** | 3 | 4 → 12 bits | 2416 |
| Hero 1–3 | 0 → 4 bits | **1 → 5 bits** | 3 | 3 → 11 bits | 1336 |
| Hero 4 | 0 → 4 bits | 2 → 6 bits | 38 | 4 → 12 bits | 2139 |
| Hero 5 | 0 → 4 bits | 2 → 6 bits | 33 | 3 → 11 bits | 1365 |
| Hero 6 | 0 → 4 bits | 2 → 6 bits | 36 | 3 → 11 bits | 1251 |
| Hero 7 | 0 → 4 bits | 2 → 6 bits | 36 | 3 → 11 bits | 1249 |

**Professions and skills follow "the smallest width that fits the largest value".** Profession
ids reach 10, needing 4 bits, and code 0 gives exactly 4. Skill id 2416 needs 12 bits and gets
code 4 (12); 1365 needs 11 and gets code 3 (11). Every row is the tightest fit.

**Attributes do not, at the low end.** The two Mesmer builds store ids 0, 2 and 3 — two bits
would hold them, and code 0 would give four — yet both use code 1 (five bits). The rule that
fits all seven is:

```text
profession width code = smallest code with  code × 2 + 4 ≥ bits(max profession id)
attribute  width code = max(1, smallest code with  code + 4 ≥ bits(max attribute id))
skill      width code = smallest code with  code + 8 ≥ bits(max skill id)
```

**The `max(1,...)` on attributes is inferred from two codes, not derived from a rule the wiki
states.** It reproduces every code we have, and both codes that constrain it are Mesmer bars,
so it is possible the real rule is something else that happens to agree. T1.3.5 round-trips
all seven, which will catch it if a future code disagrees; if one ever does, this is the line
to revisit. Recorded here rather than buried in the codec.

## 4. Equipment template format (type 15)

From the Equipment template format page.

| Field | Bits | Notes |
| --- | --- | --- |
| Template type | 4 | **15** (`0xF`) |
| Version | 4 | 0 |
| Item id width | 4 | |
| Modifier id width | 4 | |
| Item count | 3 | |
| *per item:* slot | 3 | 0 Weapon, 1 Off-hand, 2 Chest, 3 Legs, 4 Head, 5 Feet, 6 Hands |
| *per item:* item id | n | |
| *per item:* modifier count | 2 | |
| *per item:* dye | 4 | |
| *per item:* modifier ids | n each | |

**Three differences from the skill format that are easy to get wrong:**

1. **The width fields are raw bit counts, not codes.** There is no `+4` or `+8`. Applying the
   skill format's offsets here would misread every field after the header.
2. **The dye sits between the modifier count and the modifier list**, not after the
   modifiers. Reading them in struct order rather than wire order silently shifts everything.
3. **The legacy header's version is 1, not 0.** A pre-2007 skill template has version 0; a
   pre-2007 equipment template has version 1. So a bare `0` nibble means a legacy *skill*
   template and a bare `1` means a legacy *equipment* template.

**Dye values:** 2 Blue, 3 Green, 4 Purple, 5 Red, 6 Yellow, 7 Brown, 8 Orange, 9 Silver.
0 and 10–13 are preview-only and load as silver. **1, 14 and 15 make the code invalid.**

**Two versions are in circulation.** The page gives worked examples of both a version 1 and a
version 0 equipment string. Only version 0 is specified above; a version 1 code is out of
scope until something needs it.

### Equipment templates describe PvP equipment

Worth stating plainly, because it changes how much this matters: the item id list is
`PvP Axe`, `PvP Longbow`, `PvP Restoration Staff` and so on, and equipment templates can only
be loaded by PvP characters. gwsim simulates **PvE**. So the equipment codec is for *reading*
codes that a published build happens to include, not for describing a gwsim build's gear.
`Build::to_templates` (T1.4.9) can still emit one, but it is a lossy view of a PvE build.

| Hero 6 | `OACjEyiM5MXTvJzEAINncDzxJ` | Rt / — | Resto 12, Chan 12, Spawn 3 | Signet of Spirits, Ancestors' Rage, Spirit Siphon, —, Mend Body and Soul, Spirit Light, Protective Was Kaolai, Life |
| Hero 7 | `OACiAyk8gNtePuwJ00ZaNBAA` | Rt / — | Communing 12, Spawn 12 | Soul Twisting, Shelter, Union, Displacement, Armor of Unfeeling, Boon of Creation, Signet of Creation, — |

Three things this confirms, each of which would otherwise be a surprise later:

- **The elite slot is often empty.** The player's code has three empty slots and Hero 1–3's
  code has no elite at all — Panic is the hero's elite in §20.1 but is not in the code. The
  codes capture one choice among PvX's alternatives, as §20.1 warns.
- **Hero 1–3's code stores Inspiration 6**, where §20.1's table says 6+1. The +1 is a rune,
  and runes are not in a skill template.
- **Hero 7 stores only two attributes.** A code stores the attributes that have points, not
  every attribute the professions grant.

## 7. Decisions

| # | Decision |
| --- | --- |
| 1 | Hand-roll the Base64 and bit reader. The format is custom — six bits per character, lowest bit first — so a Base64 crate would not help |
| 2 | Attribute width code has a floor of 1, inferred from the two Mesmer codes. Flagged as the line to revisit if a code fails to round-trip |
| 3 | Skill ids stay raw in the codec. Resolving them to names needs a `DataSet`, which T1.4.9 has and the codec should not |
| 4 | Equipment templates decode and re-encode, but are understood as PvP gear; unknown item and modifier ids are kept as raw numbers so an unknown code still round-trips |
| 5 | The full 1,517-skill id list is not committed. The 72 M1 ids above are what the project needs; the extractor reads the rest in P2 |

## 8. Open questions

1. **The attribute width floor.** See §3. Only two codes constrain it, and both are Mesmer.
2. **Equipment template version 1.** A second, older layout exists and is not specified here.
   Nothing needs it yet.
3. **Whether a bar with 8 real skills changes the skill width.** Every code we have has at
   least one empty slot. Nothing suggests it would, but no vector proves it.

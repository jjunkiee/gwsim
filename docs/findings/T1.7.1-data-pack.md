# T1.7.1 Data pack format and embedding

**Task:** T1.7.1 (P1, WP1.7) · **Type:** Research / Decision · **Date:** 2026-09-22

**Question:** how should a shipped binary carry `data/`, so that it runs with no data
directory present?

**Method:** the three options were compared on measured start-up cost, not estimated. A
synthetic tree the size of full coverage was built and loaded through the WP1.2 loader. The
benchmark is committed as `crates/gwsim-data/tests/pack_scale.rs`, ignored by default, so the
measurement can be repeated when the tree is real.

---

## 1. The decision

**Option (a): embed the RON text and parse it at start-up.**

The plan expected option (b) — validate at build time and embed a `postcard` or `bincode`
serialisation. **The measurement does not support that.**

## 2. What was measured

A synthetic tree of **2,000 skills and 400 foes: 2,400 files, 2.9 MB**. Each skill carries a
full encoding — three actions including a nested `If` and a `Secondary` selector, an effect
definition, two extracted scaled numbers and a provenance block — so it is a fair stand-in for
a real file rather than a stub.

| Build | Best of three | Per file |
| --- | --- | --- |
| **Release** | **36 ms** | 15 µs |
| Debug | 348 ms | 145 µs |

Release is what ships, and 36 ms is not a start-up cost worth engineering around. For
comparison, it is roughly the time a single frame takes at 30 fps.

Debug is ten times slower, which is worth knowing but not worth optimising: a developer
running `gwsim data validate` in a debug build pays a third of a second once.

## 3. Why (a) rather than (b)

The plan's reasoning for (b) was start-up cost. That reason does not survive the measurement,
and (b) carries four costs that (a) does not:

1. **A dependency.** `postcard` or `bincode`, plus whatever they pull in.
2. **A second format to keep working.** Every schema change has to round-trip through it, and
   a serialisation bug is a class of failure that (a) simply cannot have — if the embedded
   text parses in the binary, it parses the same way it does from disk, because it *is* the
   same text going through the same parser.
3. **A format version to maintain**, and a failure mode where an old binary meets a new pack.
4. **Harder debugging.** A developer who wants to know what the binary thinks a skill says can
   read embedded RON. A binary blob needs a tool.

**Option (c), zero-copy with `rkyv`, was not measured.** It optimises a cost that is already
36 ms, in exchange for a much larger constraint on how the data types are written. It is the
wrong trade at this size.

**What would change this.** If full coverage turns out to be far larger than §22 expects — say
20,000 files rather than 2,400 — release start-up would approach a third of a second and (b)
becomes worth revisiting. The benchmark exists so that is a measurement rather than an
argument.

## 4. Build-time validation still happens

Choosing (a) does **not** mean shipping unvalidated data. `build.rs` loads and validates the
tree at build time and fails the build on any error. What differs from (b) is only what gets
embedded: the text that was validated, rather than a derived artefact.

This keeps the guarantee the plan wanted — a release binary cannot contain a broken data tree
— without the format.

## 5. Embedding

`build.rs` in `gwsim-cli`:

- declares `cargo:rerun-if-changed=../../data`, so editing a data file rebuilds;
- loads and validates through `gwsim-data`, which is a **build-dependency**;
- on failure, prints the validation report and fails the build;
- writes a single concatenated pack to `OUT_DIR`, read with `include_bytes!`.

The pack is one file rather than many `include_str!`s because the file *list* is part of what
must be embedded: the loader routes by path, so the paths have to survive.

`pack::build_from_dir` lives in `gwsim-data` so the desktop app reuses it in P6 (T1.7.3).

## 6. The content hash

The pack carries a hash of its contents, which becomes part of the reproducibility key
(ENG-43) and is shown by `gwsim --version`.

**Decision: BLAKE3**, over the sorted `(path, contents)` pairs.

- **Sorted** so the hash does not depend on directory listing order.
- **Paths with forward slashes**, which `DataSource` already guarantees, so Windows and Linux
  agree. This was designed for in T1.2.7 and is what makes the hash portable.
- **A real hash rather than a hand-rolled one**, because the hash's job is to say "these two
  runs used the same data". A collision would silently misattribute a result, and the cost of
  avoiding that is one small dependency.

## 7. Decisions

| # | Decision |
| --- | --- |
| 1 | Embed RON text and parse at start-up. 36 ms at full coverage in release |
| 2 | Validate at build time and fail the build, so the embedded text is always sound |
| 3 | One concatenated pack file, because the paths are part of the data |
| 4 | BLAKE3 over sorted, forward-slash `(path, contents)` pairs |
| 5 | Keep `pack_scale.rs` as an ignored benchmark, so the decision can be re-tested |

## 8. Open questions

1. **Is 2,400 files the right scale?** §22 estimates ~1,400 skills. 2,400 files allows for
   foes, encounters and items on top. If the real tree lands far above this, re-measure.
2. **Debug start-up at ten times release** is fine now. If a developer workflow starts loading
   the tree repeatedly — a watch mode, say — caching becomes worth it.

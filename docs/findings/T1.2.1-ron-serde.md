# T1.2.1 RON and serde error reporting

**Task:** T1.2.1 (P1, WP1.2) · **Type:** Research · **Date:** 2026-09-22

**Question:** how does RON report errors, which extensions should gwsim enable, and how do
we attach a field path to a semantic error?

**Method:** `ron` **0.12.2** was measured directly, with a throwaway example that fed it
valid and broken input and printed what came back. Everything below is observed output,
not documentation. The probe was deleted once this was written; the cases it covered are
now the T1.2.10 fixture suite.

---

## 1. The plan's central assumption is out of date

The task as written says:

> Confirm that RON offers no span per field, so the plan is file plus field path for
> semantic errors and file plus line and column for syntax errors.

**That is not true of RON 0.12.** Semantic errors carry spans exactly as syntax errors do:

| Broken input | Reported |
| --- | --- |
| unknown field `extra` | `4:33-4:38: Unexpected field named `extra` in `Inner`, expected either `kind` or `amount` instead` |
| unknown variant `Frost` | `4:16-4:21: Unexpected variant named `Frost` in enum `Kind`, expected one of `Fire`, `Cold`, `Scaled`, or `Ranged` instead` |
| missing field `amount` | `4:20: Unexpected missing field named `amount` in `Inner`` |
| `"three"` where an integer belongs | `4:29-4:30: Expected integer` |

So the two-tier plan (positions for syntax, paths for semantics) is unnecessary. **Every
error gets a position.** The field path becomes a bonus that makes deep errors readable,
not the only handle we have.

This is good news for T1.2.9 and T1.2.10: the "good errors" standard the snapshots enforce
is cheaper to reach than the plan budgeted for.

## 2. The error type

`ron::from_str::<T>` returns `Result<T, ron::error::SpannedError>`:

```rust
SpannedError {
    code: ron::Error,
    span: Span { start: Position { line, col }, end: Position { line, col } },
}
```

**It is `span`, not `position`.** The task text names `ron::error::SpannedError` correctly
but the field it implies (`position`) does not exist in 0.12; code written against an older
API will not compile. Lines and columns are **1-based**, which matches what an editor shows.

`Display` already renders `line:col-line:col: message`, so the cheapest correct thing is to
print the error and prefix the file path.

### The codes are structured, not just strings

This is worth more than the text:

```rust
NoSuchStructField { expected: ["kind", "amount"], found: "extra", outer: Some("Inner") }
NoSuchEnumVariant { expected: ["Fire", "Cold", "Scaled", "Ranged"], found: "Frost", outer: Some("Kind") }
MissingStructField { field: "amount", outer: Some("Inner") }
ExpectedDifferentStructName { expected: "S", found: "not" }
ExpectedNamedStructLike("S")
```

`expected` and `found` are available as data, so T1.2.9 can suggest a correction ("did you
mean `amount`?") without parsing the message back out. Recommended for the unknown-field
and unknown-variant cases, which are the two a data author hits most.

### Empty and garbage files

An empty file reports `1:1: Expected opening '(' for struct 'S'`, naming the type it wanted.
A file of prose reports `Expected struct 'S' but found 'not'`. Both are good enough to ship
as-is; neither needs special handling.

## 3. `deny_unknown_fields` works, and should be on everywhere

A typo'd field name fails, with a position and the list of fields that were expected. This
is the single most valuable guard for hand-written data: without it, `recharge_time: 5`
beside a real `recharge` field would parse and silently do nothing.

**Decision: every schema struct carries `#[serde(deny_unknown_fields)]`.** It is already on
`Provenance` and the core file types from WP1.1.

## 4. Extensions: enable none

RON extensions can be turned on per file with `#![enable(...)]` on the first line, or
globally through `ron::Options::default().with_default_extension(...)`. Both were tested and
both work.

**Decision: gwsim enables no extensions.** Three reasons:

1. **The design already assumes explicit.** §8.3's worked skill file writes
   `attribute: Some(FireMagic)` and `projectile: Some(Standard)`. Matching the spec costs
   nothing.
2. **An extension changes what a file means.** The extractor (P2) writes files that must
   round-trip, and a file written under one setting and read under another is a silent data
   bug rather than a loud one.
3. **`unwrap_variant_newtypes` is actively risky here.** The effect DSL (WP1.5) has both
   tuple variants like `Scaled(7, 112)` and struct variants like `Ranged(low: 1, high: 2)`.
   Unwrapping blurs the two.

**The decision is reversible, and in the safe direction.** This was checked, because it is
the sort of thing that quietly becomes permanent:

| | parses under default | parses under `implicit_some` |
| --- | --- | --- |
| `a: Some(1)` (explicit) | ✔ | **✔** |
| `a: 1` (implicit) | ✘ `Expected option` | ✔ |

So `implicit_some` can be switched on later and **every file written today still parses**.
Had we started implicit, switching it off would have broken all of them. Starting strict is
the one-way door we can still walk back through.

## 5. Field paths: `serde_path_to_error` works with RON

```rust
let mut de = ron::Deserializer::from_str(text)?;
serde_path_to_error::deserialize::<_, T>(&mut de)
```

Measured paths:

| Defect | Path |
| --- | --- |
| unknown field in the second list entry | `inner[1].extra` |
| wrong type in the third list entry | `inner[2].amount` |
| missing field in the second list entry | `inner[1]` |

Exactly the `effects[2].amount` shape the task asked for.

**The catch:** `serde_path_to_error::Error` wraps `ron::Error`, which is the *code* only —
the span does not survive. So the two routes are complementary, and neither gives both.

**Decision: parse once, and re-parse only to enrich an error.**

```text
ron::from_str::<T>(text)
  ├─ Ok  → done. One parse, no cost.
  └─ Err(spanned) → re-parse through serde_path_to_error to recover the field path,
                    then report file + line:col + field path + the structured code.
```

The second parse happens only on the failure path, where the file is about to be rejected
anyway, so its cost does not matter. If the second parse somehow succeeds — it should not,
but data code should not assume — the span-only message is still reported.

`serde_path_to_error` 0.1.20 is added as a **dev-dependency for now** and moves to a normal
dependency in T1.2.7, when the tree loader is the thing producing these messages.

## 6. Serialisation round-trips

T1.2.3 requires an illustrative skill file to survive deserialise → serialise → deserialise
unchanged. Measured with `ron::ser::to_string_pretty` and `PrettyConfig::default()`:

- plain structs, `Option`, and `Vec<(Enum, f32)>` round-trip equal;
- **tuple variants** (`Scaled(7, 112)`) and **struct variants** (`Ranged(low: 1, high: 2)`)
  both round-trip equal.

No custom serialiser is needed. Note that pretty output puts a struct variant's fields on
their own lines, so a round-tripped file is not byte-identical to a hand-written one — the
test must compare **values**, not text.

## 7. Dates

Confirmed as the task proposed: a small validated `IsoDate` newtype, no date crate. It was
built in WP1.1 (`crates/gwsim-data/src/ids.rs`) because the core files' provenance blocks
needed it first. It stores the original string, so round-tripping is exact, and rejects
`2026-9-22`, `2026-13-01` and `2026-09-32`.

## 8. Decisions

| # | Decision |
| --- | --- |
| 1 | Every schema struct carries `#[serde(deny_unknown_fields)]` |
| 2 | No RON extensions. Reversible later towards `implicit_some`, not away from it |
| 3 | `ron::from_str` on the happy path; a second parse through `serde_path_to_error` only to enrich an error |
| 4 | Errors report file + `line:col` + field path + a message derived from the structured code |
| 5 | Use `expected` / `found` from `NoSuchStructField` and `NoSuchEnumVariant` to suggest corrections |
| 6 | `IsoDate` newtype, no date crate (built in WP1.1) |
| 7 | Round-trip tests compare values, not text |

## 9. Corrections to the plan

- **T1.2.1's premise that RON has no per-field span is wrong for 0.12.** Semantic errors
  carry spans. The plan's two-tier error model can be simplified to one tier.
- **`SpannedError.position` does not exist**; it is `.span`, holding a start and end
  `Position`.

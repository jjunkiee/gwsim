## Profilers

| Tool | For | Against |
| --- | --- | --- |
| **samply** | `cargo install samply`, no administrator rights. Samples through ETW on Windows and opens the Firefox Profiler with Rust symbols from the PDBs. | ETW sampling needs an elevated terminal the first time. |
| Visual Studio profiler | Excellent call trees. | Needs the Visual Studio IDE; the Build Tools alone do not include it. |

Temporary counters (`touch`-style per-site counters and `Instant` timing around suspect loops) found the hot paths. They took a fight from 47 ms to 7.5 ms and were then removed ([T4.11.6](T4.11.6-performance.md)).

## Making a CI performance check useful

GitHub's shared runners vary by well over 20% from run to run, so a wall-clock threshold at the §17.6 20% rule would fail at random. The options were:

1. **A relative check against a baseline run in the same job.** This still depends on the noise and doubles the time.
2. **A generous absolute threshold.** It is stable but only catches gross regressions.
3. **Counting the work per fight as a proxy.** It is deterministic and exact, and it catches algorithmic regressions (more events, more re-scheduling) at any tolerance. It misses regressions that make each event slower without adding events.

**Chosen: 3 and 2 together** (`crates/gwsim-engine/tests/perf_smoke.rs`, run by CI in release):

- The mean events dispatched per Kournan patrol fight over 16 seeds must stay **within 20% of a recorded baseline** (1,085). A model change that adds work on purpose updates the baseline in the same commit and gives the reason.
- The mean wall time per fight must stay **under 50 ms** in release, five times the D19 target. This catches only accidents such as a quadratic loop, but it never fails on noise.

The criterion benchmarks (`cargo bench -p gwsim-engine`) remain the tool for real measurement on a quiet machine.

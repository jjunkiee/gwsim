## 2. The `windows-latest` runner

`windows-latest` currently maps to **Windows Server 2025** (x64). Other labels available:
`windows-2025`, `windows-2025-vs2026`, `windows-2022`, `windows-11-arm`,
`windows-11-vs2026-arm`. GitHub announces `-latest` moves ahead of time.

**MSVC is preinstalled:** Visual Studio **Enterprise 2022** (17.14.37628.2) at
`C:\Program Files\Microsoft Visual Studio\2022\Enterprise`, with the MSVC toolchains for
x86, x64, ARM and ARM64. So CI needs no Build Tools install step, and `link.exe` is
present.

**Rust is preinstalled too**, and at exactly the version the development machine will have:

| Tool | Version on the runner |
| --- | --- |
| Rust / Cargo | 1.98.1 |
| rustup | 1.29.1 |
| clippy | 0.1.98 |
| rustfmt | 1.9.0 |

Two things follow. First, CI and the development machine match, so a CI-only failure is a
real signal rather than a version difference. Second, note that the runner ships VS **2022**
while the development machine will get Build Tools **2026** (T0.1.1) — the same MSVC
component IDs, but not the same edition. Worth remembering if a linker-level difference
ever appears.

## 3. Do we still need the toolchain action?

Strictly, no: rustup is preinstalled, and our `rust-toolchain.toml` (`channel = "stable"`,
`components = ["rustfmt", "clippy"]`) makes rustup install and select the right toolchain
automatically on the first `cargo` call.

**Decision: keep `dtolnay/rust-toolchain@stable` anyway.** It costs a few seconds, it makes
the installed toolchain explicit in the log instead of implicit, and it protects us if a
future runner image drops the preinstalled Rust. There is no conflict with
`rust-toolchain.toml`, because both name `stable`.

## 4. Windows only, or add Linux?

**Decision: one `windows-latest` job for now**, matching the plan's recommendation.

Windows is gwsim's official and only supported platform (§18.2), so it is the platform that
must be green. Adding an `ubuntu-latest` job for `fmt` and `clippy` would return results
faster and cost less, but it would also be the first thing tempting us to care about a
platform we do not ship. Revisit only if Windows CI time becomes a problem — the trigger to
watch is the performance smoke test added in T4.11.5.

## 5. Shape of the workflow

- **Triggers:** `push` and `pull_request`.
- **`permissions: contents: read`** — the workflow only reads the repository; least
  privilege by default.
- **`concurrency`** grouped by ref with `cancel-in-progress: true`, so a new push
  supersedes the in-flight run on the same branch.
- **Steps:** checkout → toolchain → cache → `fmt --check` → `clippy -D warnings` →
  `test --workspace`. Formatting first because it is the cheapest way to fail.

Placeholders are added as comments naming the task that turns each one on: `gwsim data
validate` (T1.2.12), reduced relative checks (T4.10.6), performance smoke test (T4.11.5).

## 6. When this first runs

**Not yet.** The repository has no remote (T0.4.1: `origin` is unset). The workflow is
written now so it is ready, and its first real execution happens when the owner creates a
GitHub remote and pushes. Until then T0.6.5 reviews it by eye.
